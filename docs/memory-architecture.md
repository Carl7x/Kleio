# Kleio 记忆：M1 / M2

## 修复什么

旧实现把完整用户消息切成中文双字词，再用 OR 匹配已保存事实，每一步自动注入结果。这种宽松命中会把只有微弱词汇重合的研发方向带到无关的工具讨论中。新版移除这条路径，没有“截图就不提 Personal Agent”这样的特例。

新版读路径：

1. 第一次组装会话上下文时，读取 SOUL、MEMORY、people/groups INDEX，并为当前 Agent 冻结这份开局快照。
2. System prompt 要求每轮先 `memory_search`，模型构造2–3个当前话题的短查询。每个查询的完整词项必须同时出现在同一段记忆或同一条历史消息中。
3. 文件命中返回路径、行号和正文摘要；历史命中返回会话、事件序号、角色、时间。必要时用 `memory_get` 读正文。
4. 模型判断来源是否相关、是否已过时、能否用于当前问题。不相关就不用；无结果就不补上“最近的项目”。

移除旧的 Agent `personal_memory_recall` 入口，避免模型在纠错时绕开文件/历史检索。`memory_search.facts` 同时返回正式事实的 id/version，纠错和普通回复共用一条读路径。

这项“每轮先检索”目前是模型行为指令，原生工具执行和日志可以验证是否遵守；尚未加入强制拦截最终回答的 runtime 检索门禁。

## 文件、索引、审计的边界

`MEMORY.md` 是可以直接编辑的常驻摘要。具体项目默认不自动升入此文件；显式保存时，模型仅对跨话题适用的身份/沟通偏好选择 `standing=true`。这减少开局偏置，不等于禁止项目记忆。

people/groups 索引只是目录，不代表用户目前的任务。它们与主题页都是自有的 Markdown 文件。每日文件追加变更时间、路径、来源与更正引用，不保存凭据或工具参数。

已有的正式事实继续使用事务、版本、审核回执和可撤销删除；每次提交后导出当前事实页。SQLite 用于这条兼容审计路径及可重建的历史文本索引，**并非完整的纯文件数据库实现**。事实页是当前版本的投影，不能直接改写；更正通过正式工具或界面，同步精选页和主题页。自定义主题笔记则直接以 Markdown 为源。

模型从每轮真实的人类消息获得写入来源；网页、工具结果、后台子任务不能自己授权改个人事实。普通陈述先进入待确认候选，尚不实现无条件自动升入 L1。

## 历史对话全文

启动时读取原生本地 `session.v4.jsonl.zstd`，支持多个压缩帧；运行中监听原生 session 事件。只索引直接用户文本和对外的助理文本，排除 system/developer、推理、工具结果及委派会话。历史话语始终带角色，不会自动成为用户事实。

查询使用完整词项 AND，而不是中文 bigram OR。英文大小写与全角字符归一化，引用内容保留原文。历史范围包含其他会话及本会话当前轮之前的消息。凭据行和带 token 的链接被排除。

当前上限：启动导入最多500个会话，单文件16MiB、解压总量32MiB，单条文本64,000字符。超限/损坏计入 indexHealth；超限会话需要之后做增量分页，不宣称无限历史召回。文件读取限128KiB、单次120行；精选内容应低于100行，超过120行拒绝开局注入而不是静默截断。

这是全文匹配，没有 embedding、同义词扩展或排序模型。“企微”不会自然命中“企业微信”；M4 才解决这个问题。SQLite 索引可以从原生日志重建。

## 参考项目的取舍

| 参考 | 采用的流程 | 不直接采用的部分 |
| --- | --- | --- |
| 用户提供的 Muse 说明 | 开局小抄、每轮检索、模型关联；SOUL 与个人资料分开 | Muse 的向量库/排序属于未知 runtime，不能据此声称复刻其内部实现 |
| [OpenMausBot 的 memory 文档](https://github.com/milind-soni/OpenMausBot/blob/main/docs/memory.md) | Markdown 摘要、主题页、每日记录、有限注入、原子写入 | 不把全部资料常驻；本阶段不照搬其定期整理与自动归档 |
| [OpenGrok memory/goals](https://github.com/mweinbach/open-grok/blob/main/docs/agents/memory-and-goals.md) | memory_search / memory_get、文件与会话索引、稳定的开局快照 | 不立即引入 hybrid 向量、dreaming、MMR；这不是 Muse 官方源代码 |
| [nanoMuse](https://github.com/nano-muse/nanoMuse) | 记忆、目标、召回职责分开，可参考其整理测试 | 不沿用中文双字词 OR 宽松召回，也不搬入 Python 产品内核 |
| [OpenBot](https://github.com/CopilotKit/OpenBot) | 事实来源、作用域、用户审核的设计原则 | 不用候选推断替代用户确认 |
| [OpenMuse](https://github.com/CopilotKit/OpenMuse) | 个人助理界面、资料与持久记忆编辑入口 | 它不证明 Muse 闭源产品的召回排序实现；不据此照抄未知 runtime |

参考实现是设计证据，不是把多个项目代码混装。Kleio 的新增文件层和历史索引由本仓库实现，底层会话、工具、权限、任务执行仍归 Harness。

## 验证和下一步

独立用例包括截图、镜头、旅行行李、食谱；同时覆盖多词项不完整命中、同义词不匹配、身份/项目分层、纠错/遗忘、历史用户与助理角色、注入消息排除、跨目录读取拒绝、多帧原生会话恢复。隔离资料不会写入用户正式数据。

M3：统一 claim kind/confidence/source/supersede 与会话结束 distill，完善人物与群体提炼。

M4：embedding 索引、reconcile、后台准备器和主 Agent 审核通知。定时唤醒与委派已存在，但防打扰通知链尚需单独实现。不要把执行完成和应当打扰用户混为一件事。
